# 프로젝트 워크스페이스

Windows에서 `Launch-Windows.cmd`로 시작합니다. 소스에서 통합 터미널과 시스템 지표를 사용하려면 `py -3 -m pip install -r requirements-desktop.txt`를 실행합니다. 배포용 Windows 번들은 `.\Build-Windows.ps1 -InstallBuildDependency`로 만듭니다. SSH를 쓰려면 Windows OpenSSH Client의 `ssh.exe`와 `ssh-keyscan.exe`를 사용할 수 있어야 합니다.

## 프로젝트와 작업 시작

1. **프로젝트 → 로컬 저장소 추가**에서 Git 폴더를 선택합니다. 앱이 저장소 루트, 현재 브랜치, origin, 기술 스택과 안내용 QA 명령을 조회합니다.
2. 프로젝트 탭에서 기본 모델, Harness, 변경 경로, MCP 도구와 QA 명령을 저장합니다. 탐지된 QA 명령을 사용할지 검토합니다.
3. **새 작업 → 계획 만들기**에서 작업을 자연어로 입력하고 **읽기 전용 분석**, **변경 · 검토 · QA**, **검증 명령만** 중 하나를 고릅니다. 계획은 선택한 전략과 기본값으로 생성됩니다.
4. 생성된 노드와 선행 조건을 검토합니다. 필요하면 **노드 편집**에서 권한을 바꾸고, 예상 실행 경로와 QA 명령을 승인합니다. 작업·레지스트리의 고급 JSON 편집도 사용할 수 있습니다.

예를 들어 ‘백엔드 구조를 살펴보고 개선할 부분을 근거와 함께 알려줘’는 Explorer 계획으로 시작할 수 있습니다. 코드 변경을 고르면 변경 경로와 통합 QA가 필요합니다. 모델 없이 시작하려면 검증 전략에서 `git --version`을 실행할 수 있습니다.

## Provider와 모델

**설정 → Provider 설정 마법사**에서 Ollama, llama.cpp, 로컬 OpenAI 호환 엔드포인트, OpenCode 또는 Codex를 등록합니다. Runtime 연결 확인은 모델 목록을 읽고 응답 시간을 표시합니다. 목록에서 관측된 Context와 직접 입력한 값을 구분하며, 실제 실행에서 기존 Runtime 검증을 통과해야 합니다.

CLI 탐색은 경로를 확인할 수 있습니다. 지원 CLI에서는 실행 파일을 신뢰한다고 선택한 뒤 버전 명령을 시험할 수 있습니다. CLI 로그인, Vision 및 추론 능력은 이 결과로 확인되지 않습니다. Gemini CLI, Claude Code, Antigravity 등은 설치 탐색 대상이며 추가 실행 어댑터는 남아 있습니다. 직접 API 키 입력 대신 환경 변수 참조 또는 외부 CLI 로그인 저장소를 사용합니다.

**모델·Runtime 편집**에서 허용 역할·Harness, 예산·라우팅 점수, Runtime 한도와 인증 참조를 수정합니다. 고급 JSON 레지스트리는 버전 1로 저장하며 기존 파일은 덮어쓰기 전에 `backups/registry.json`에 보관합니다. 프로젝트와 SSH 프로필은 독립적인 `workspace.json`에 저장합니다.

## Agent와 터미널

**Agent 대시보드**는 실제 노드 상태, 실행 경로, 관측된 토큰 수, 도구 호출, 변경 파일 및 결과를 보여 줍니다. 이벤트 검색으로 실패·QA·도구 호출을 좁힐 수 있습니다. **오케스트레이션**에서는 노드 의존성을 클릭해 Agent 상세를 열거나 두 실행 보고서를 비교합니다. **작업 실행**에서는 필수 QA와 후보 SHA가 저장된 뒤 기존 승인 흐름으로 병합합니다.

**통합 터미널**의 로컬 셸과 SSH 셸은 사용자 조작용 PTY입니다. 여러 탭과 탭 분할, ANSI 출력, 입력, 크기 조절을 지원합니다. 세션 다시 열기는 새 셸을 시작합니다. Supervisor의 비대화형 Agent 프로세스는 구조화된 이벤트로 조회하며 완료한 노드의 Worktree에는 별도 셸을 열 수 있습니다.

## SSH와 Linux Worker

1. 서버에 Python 3.11 이상과 Git을 준비하고 이 프로젝트의 `orchestra/`와 `ModelOrchestration.pyw`를 같은 소스 디렉터리에 배치합니다.
2. 서버의 같은 사용자 계정으로 소스 디렉터리에서 `python3 -m orchestra.remote --register /absolute/path/to/repo`를 실행합니다. 경로는 허용 저장소 목록에 추가됩니다. Worker 설정은 기본 데이터 폴더의 `remote-worker/` 아래에 있습니다.
3. 필요한 경우 서버가 신뢰하는 설정만 Worker의 `registry.json`에 등록합니다. 파일 변경 작업을 허용할 때는 등록 명령에 `--allow-background-write`를 명시합니다. 업로드는 `--allow-upload`로 별도 활성화합니다.
4. 작업 공간의 **+ 추가 → SSH 호스트 추가**에서 사용자 홈의 `~/.ssh/config` 별칭을 선택합니다. 별도로 추가하려면 사용자, 주소, 포트(기본 22), 키 파일(선택)을 직접 입력합니다. Worker를 사용하는 경우 **고급 설정**에 Worker 소스 경로와 필요에 따라 Python 3.11 이상의 절대 경로를 입력합니다.
5. **연결 테스트**를 누르면 처음 연결할 때 서버 지문 확인 창이 열립니다. 서버 관리자가 별도 경로로 제공한 공개 지문을 입력하면 연결 테스트가 이어집니다. 연결에 성공한 뒤 **프로젝트 → 원격 저장소 추가**에서 Worker가 허용한 저장소를 선택합니다.
6. 원격 프로젝트에서 계획을 제출합니다. 한 DAG는 선택한 Linux 서버에서 실행됩니다. 앱을 닫거나 SSH가 끊겨도 서버의 Supervisor가 작업을 유지합니다. **원격 작업 → 다시 연결**로 같은 실행을 조회합니다.

별칭을 선택하면 `HostName`, `User`, `Port`와 첫 번째로 지원되는 절대 `IdentityFile` 경로를 채웁니다. `.ssh` 안의 `Include` 파일도 읽습니다. 원본 설정이 바뀌면 호스트 편집에서 별칭을 다시 선택하고 저장하세요. 앱은 자체 지문 검증을 거쳐 서버에 직접 연결합니다. `ProxyJump`, `ProxyCommand`, `Match` 및 포워딩은 적용되지 않습니다.

원격 파일 창에서 일반 파일과 디렉터리를 탐색하거나 200 KB 이하 파일을 다운로드할 수 있습니다. 허용된 업로드는 확인 후 서버의 Worker 보관 폴더에 저장됩니다. 서버가 포그라운드 SSH 로그인에 암호가 필요한 키를 쓴다면 백그라운드 API 호출에 앞서 SSH Agent에서 키를 해제하세요. Windows 서버용 SSH 경로는 터미널·연결 확인 범위이며 네이티브 테스트는 남아 있습니다.

## MCP와 문제 해결

**MCP 및 도구**에서 기존 CLI 설정을 탐색하고, 별도 Managed 프로필에 서버와 읽기·쓰기 정책을 등록합니다. Agent 제한은 `역할/노드ID` 형식입니다. 기존 Federated 연결은 사용자의 전환을 통해서만 바뀝니다. 외부 쓰기 및 병합에는 기존 승인 절차가 적용됩니다.

- 모델이 나오지 않으면 연결 확인의 모델 목록, 프로젝트 실행 위치, 모델 역할 및 Harness 제한을 확인합니다.
- SSH 지문이 바뀌었다면 서버 관리자를 통해 값을 확인한 뒤 신뢰 지문을 다시 등록합니다.
- 원격 작업 연결이 끊겼다면 기존 작업의 **다시 연결**을 사용해 동일 요청 ID를 복구합니다.
- 자격 증명 값이나 개인 키 내용은 JSON에 입력하지 않습니다.

OpenSSH가 수집한 키의 인증 한계와 고정 키 설정은 [ssh-keyscan 매뉴얼](https://man.openbsd.org/ssh-keyscan)과 [ssh_config 매뉴얼](https://man.openbsd.org/ssh_config)을 참고하세요.
